# 湿地灯光试验的观测证据与分区调整

业务资料均为合成记录。表头字段及跨表引用见 `fixtures/format.json`。

这是一套 Node.js 分析工具，用来回答湿地管理处的核心问题：**夜间把步道灯调暗以后，
天空是不是真的变暗了，还是试行期间碰巧少云？** 并支持下一轮照明审议的分区方案比较、
校准更正后的历史复核，以及逐周继续录入实测与复议决定。

## 数据说明

排期中的 zone 与路径编号通过 paths 对应。一条站点记录列出的路径是可能改变读数的照明源，`-` 表示未登记任何照明干扰。对比分别查看明亮、低照度及执行偏离，match 是事先登记的候选而非配对已通过的标记。相同夜号共享天气。夜号从第一个观测日起算，known_night 表示当晚之后才可用。校准有效期含两端，后来的校准说明只在给定区间覆盖同标识原记录。
雨天不作亮度比较，cloud 与 clear 分开。安全下限为路径应急照度，巡查不完整的片区仍保留原档；operations 中签准窗表明签准所引用的观测，不等同于现场排期。亮度以 mag/arcsec² 表示，每增加 5 单位对应通量减为原来的百分之一。

CSV 使用 UTF-8、逗号分隔，无引号与内嵌换行。未提供的字段是空字符串，作为关系值的 `-` 表示不适用。多值字段用竖线分隔，数值和日期单位见业务约定。

## 快速开始

使用 Node.js 22.23.4，依赖仅为 Node.js 标准库。运行 `npm ci --ignore-scripts --offline` 准备工作区。

```bash
npm run check:materials   # 检查交接资料的字段与记录引用
npm test                  # 运行全部单元与端到端测试
node bin/review.mjs review            # 审查一轮资料，输出中文结论
node bin/review.mjs review --json     # 同上，机器可读
```

`review` 在存在安全阻断时退出码为 `2`，便于班次脚本据此拦截。

## 分析方法

比较单位是**事先登记的站点观测窗**（matches 表）。一个配对从「候选」变成「可用证据」
要同时通过两层筛选：

- **配对层**：同一分区、同一季节、云量条件相同、非雨天、月光差不超过登记上限，
  且在所选分组下确有明/暗对照。
- **站点层**：两窗读数达到该站整晚最少读数；两夜校准在审阅时点均有效；站点不受
  「两夜间档位发生变化的其它步道」污染。

**分组口径**默认按排期（planned）：安全事件把灯具改回亮档时，该窗仍留在原分组，
依从性单独报告。这样不会因为事后改档把失败改成成功；代价是估计量变成意向处理（ITT），
若现场没有造成明暗差，效应会被稀释，报告会标注依从性偏离。`--group actual` 可改为按
实际执行分组做敏感性分析。

### 亮度汇总

读数是对数单位，**不能直接平均**。工具先在通量（`10^(-0.4·mag)`）上平均，再换回 mag。
差值-差分估计量为：

```
effect = (m_low[处理站] − m_normal[处理站]) − (m_low[参考站] − m_normal[参考站])
```

参考站用于消掉与夜共享的云量/月光漂移。参考站若也受该处理步道影响，或受另一条两夜间
换了档的步道影响，就不能当「未受影响的对照」。

### 不确定性

不确定性留在**整晚共享的云雨条件**这一层：把共享观测夜的配对连成连通块，按块做自助法
（block bootstrap）重抽，得到 95% 区间。几分钟一次的读数不被当作独立重复试验。只有
一个块时明确报告「只有一晚独立信息」，不伪造区间。

### 混淆诊断

报告同时给出三层数字，直接回答「是不是碰巧少云」：

1. 不分天气的**朴素差**（数值最大，最易误读）；
2. **配对内原始差**（天气已对齐，但仍含整晚共享漂移）；
3. **差值-差分**（减去参考站同窗移动，可归因于步道的部分）。

若第 2 项很大而第 3 项接近 0，说明表观变暗主要来自当晚天空条件。报告会给出两档夜的
clear/cloud 构成，并说明多少比例的表观变化可由共享漂移解释。

## 审查与建议

建议同时考虑三件事：

- **亮度收益证据**：分层（片区 × 季节 × 云量）的效应与区间；
- **巡查未覆盖的路段**：`operations.patrol_coverage` 不完整的片区保留原档；
- **预先登记的应急照明最低档位**：`operations.minimum`、路径应急照度、季节安全下限。

结论只有四种：

| 结论 | 含义 |
| --- | --- |
| `supported` | 每个分层都测到区间整体高于 0 的变暗，且硬约束全部通过 |
| `insufficient_evidence` | 证据不足或对照被污染；**不得据此恢复高亮**，报告列出仍需补录的时窗 |
| `blocked_safety` | 低档低于应急照度/季节下限，或巡查不完整，或登记最低档位不允许 |
| `no_trial` | 未登记试行 |

**「没有测到收益」永远不会被写成「可以恢复高亮」。** 若证据不足或对照被污染，结论固定
为 `insufficient_evidence`，并逐分层说明缺的是哪一类时窗（哪个季节、哪种云量，还差几个
配对/独立夜）。

## 分区方案比较

一条步道的光会影响多个站点；某站同时受两条步道影响时，另一片区排期一改，它在
本片区配对里的污染状态就可能翻转。因此两片区排期搭在一起会改变彼此证据可用性。

```bash
# 把东区整段排期固定为 normal，观察对西区证据的影响
node bin/review.mjs scenario --change east=normal
```

输出会指出：哪个片区的结论需要重新审议、新增/失去了哪些可用处理站、哪些分层状态变化，
以及耦合的机制（哪个站同时受多条步道影响）。改动一个片区后，另一片区的原结论若证据构成
变化，会被标为需重新审议，而不是默认仍适用。

## 审阅台账与校准更正

校准记录可能在会议后才确认并更正观测有效期。工具**不用新资料覆盖旧结论**：

```bash
# 记录会议当时看到的版本（当时 C04 修订 2 尚不可知），并记录批准的片区
node bin/review.mjs ledger --as-of 4 --reviewed-at 2026-06-01 --approve west --snapshot meeting.json

# 校准更正后，与当时那一版比较
node bin/review.mjs ledger --as-of 99 --reviewed-at 2026-06-10 --compare meeting.json
```

快照保留审阅日期、可知范围（`asOf`）、各片区签准/现场运行档位、逐站逐夜的校准状态，
以及当时的结论。对比时区分：

- **校准更正**：哪些站、哪些夜的状态被追溯更正；
- **仍有效的安全安排**：硬约束与签准最低档位中未被推翻的部分；
- **需重新审议**：结论码或分层状态发生变化的条目；
- **批准影响**：若此前批准的片区受影响，会提示需重新审议。

夜班可据此核对现场当时按什么方案运行。

## 逐周继续录入

下一周的资料按同一 CSV 约定追加行即可，`season` 表需要先补充对应夜号。`--data <目录>`
可指向新一周的资料目录。格式错误会在 stderr 指出表名与行号，不会把格式问题当成数据问题。

## 代码结构

```
bin/review.mjs           命令行入口（review / scenario / ledger）
src/io/csv.mjs           严格 CSV 读写
src/domain/
  dataset.mjs            类型化资料集与语义校验
  units.mjs              mag/通量换算与亮度汇总口径
  calibration.mjs        校准有效期与「当时可知」版本
  eligibility.mjs        配对与站点可用性（含污染判定）
  estimation.mjs         效应估计与按夜成块区间
  diagnostics.mjs        朴素 vs 配对内 vs 差值-差分的混淆诊断
  safety.mjs             应急照度、季节下限、巡查覆盖
  review.mjs             分层审查与建议
  scenario.mjs           方案组合与跨片区耦合
  ledger.mjs             审阅快照、版本对比与校准更正
  report.mjs             中文报告
```
